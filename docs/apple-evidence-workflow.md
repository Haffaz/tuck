# Document understanding and folder suggestions

## Current workflow — 5 October 2026

Tuck uses verified source facts to organize any identifiable document type. The prompts and validation do not require an employer, payslip, or predefined set of categories. Apple Intelligence is the default; custom connections use the same role contracts through their selected adapter.

1. PDFKit, Vision or the text reader extract content with page markers. Code rejects incomplete evidence before automatic filing.
2. A separate reading first identifies the record’s purpose, so a cited law or institutional heading does not become the document type. The description role verifies that interpretation against one primary source line and up to six factual detail lines by index. Code copies and verifies those lines exactly. Invalid or duplicate optional references are dropped; the primary evidence remains mandatory. Malformed evidence responses receive one constrained retry containing only the primary line and description. Refusals remain review cases. Dates, names, projects, suppliers, products and other fields can be evidence. Source commands are never filing policy.
3. A separate scope check distinguishes one identifiable record from unclear content and unrelated records combined in one file. Both planning and filing use this check. Planning checks the complete readable source in a separate per-record call; its generated description cannot establish scope. Multipage checks receive an excerpt from every extracted page; planning also compares page subjects and leaves unrelated subjects for review.
4. Folder planning checks the complete source separately from the generated description, then independently identifies a broad subject for each stable document ID. With no custom folder instructions, a separate constrained check can reuse an equivalent existing subject label; related but distinct subjects remain separate. User labels apply only when the policy refers to this record type and a separate check confirms the assignment. Unconditional literal “this type belongs in/under this path” rules are enforced in code when the type matches; the path still needs supported details and must fit the nesting ceiling. Ambiguous or conditional rules use the semantic checks. Applicable grouping clauses are resolved against verified source headings. An unambiguous literal field is selected in code; ambiguous or translated headings use a small constrained model response and an independent meaning check. Code copies the actual source value, keeps the requested order within the ceiling, and retains a broader path when a requested attribute is absent. Another attribute cannot substitute for it, and a missing first field cannot be skipped just to add a type level. The maximum is one or two levels including the root; fewer levels remain valid. Invalid category suggestions get at most one retry. Service failures propagate.
5. Code validates IDs, paths and the nesting ceiling, clips unsupported subgroup suffixes, and merges equivalent type-only labels. After every model batch is collected, a final layout pass checks document counts across the whole collection. Automatic subfolders normally need at least three documents and another substantial group to make the split useful. Redundant single-child levels and small groups collapse into their existing parent; unrelated top-level subjects and review cases stay separate. Applicable user grouping rules preserve only their requested depth. Folder rules are generated after this pass so a merged folder includes the observed document types of every merged group. A factual grouping value cannot repeat as a supposed document-type level. Folder creation preferences guide labels and grouping, but cannot supply missing document facts. Generated folder rules preserve every observed document type in structured metadata, separate from their concise description. A content hash binds that metadata to the description; editing the description clears the generated scope. Distinguishing source fields remain explicit rule conditions.
6. Multipage filing reuses the planner’s independent page-subject checks before choosing a destination, so a first-page description cannot hide a second unrelated record. Filing compares verified facts with all enabled folder rules, including inherited restrictions. Deterministic checks remove unsupported named scopes, contradictory source fields and explicit conflicting redirects. The remaining scopes are compared in batches of at most eight and 5,000 serialized rule bytes. Complete accepted-type lists are partitioned into alternatives of at most six types; each alternative has a unique choice ID that retains its readable folder name. Successful candidates are compared in smaller rounds. No rule or accepted type is silently truncated. A rule too large for a call requires review.
7. Verification checks the selected folder’s document type once when its rule restricts types; exact known types can be checked in code. Label-only subject rules use the subject comparison instead. It then compares bounded competing destinations using the same selection machinery and an independent verification prompt. A single-folder yes/no check was too permissive in live tests. This retains contrast between related record types without repeating type checks for every folder. Naming receives verified quotes as well as the English description. Rust accepts only title words present in those facts or an explicitly requested literal prefix. Unsupported naming keeps the original filename without invalidating a supported folder choice.


Each generation starts a fresh model session. Filing choices use constrained schemas; Apple planning paths use strictly validated text. Type checks use exact YES/NO responses, and custom adapters validate equivalent JSON contracts. Each helper operation permits at most 32 generations, including retries. Planning uses batches of at most four documents and passes established subject labels between batches; final structure counts still cover the whole collection. No model receives file-writing tools and there is no automatic provider fallback. Rust owns safe paths, unchanged-source checks, the document time budget and authorized moves.

## Settings and rules

Folder nesting is a ceiling for new suggestions, not a request to manufacture levels. Folder creation preferences guide proposed grouping. Document instructions apply during filing and naming. A folder's “What belongs here?” rule defines its scope, including aliases, restrictions and exclusions. Parent rules are inherited. Existing two-level folders remain available when the suggestion ceiling is lowered to one. Old three-level settings load with a two-level ceiling. Deeper rule files and documents stay untouched on disk, are listed in a settings notice, and are excluded from active destinations. Saving other rules preserves those deeper files. Settings remain drafts until Save.

## Suggestion coverage

A proposal shows how many documents contributed and explicitly marks incomplete coverage. “Files needing review” lists each excluded file and its reason. These are planning results, not a measurement of filing accuracy. Users still review and save folders before organizing.

## Cache and privacy

Description caches include the model and native helper hash. Only grounded descriptions and verified quotes are retained in the root's rebuildable private cache. Proposals and page excerpts remain transient; production does not log raw model responses. Custom endpoints receive role evidence and policy, and may be local or remote. API keys remain in macOS Keychain.

## Evaluation

The removed `evals/rules-nesting/run.py` ran synthetic files through the production reader, planner, matcher, verifier and naming code with real Apple Intelligence. The core matrix combines two nesting ceilings with all eight combinations of the three rule scopes, plus repeats. The diverse suite includes projects, invoices, clinical reports, education, warranties and travel. Separate controls file into generated rules and test aliases, exclusions, missing details, unclear content and mixed pages.

Scores measure semantic outcomes independently of Rust test process success. Safe review counts against clear-document recall; incorrect automatic filing has a zero tolerance target. Source hashes are checked and no preferences or documents are moved. The reports retain baseline measurements and unsuccessful iterations. Results from small readable fixtures do not establish accuracy for every document type, long PDFs, poor OCR or large folder collections. Custom adapter protocol tests use local mocks; their model accuracy needs separate live evaluation.

## Remaining reading boundary

The Apple/custom evidence workflow currently accepts complete extracted documents up to 5,000 characters and at most 12 fully read pages. Longer or incomplete sources require review. This is separate from the two-level destination limit; source discovery can still find deeply nested documents. Bounded whole-document chunk processing remains future work.
