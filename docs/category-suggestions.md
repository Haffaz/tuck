# Category suggestions

> Apple update, 2026-10-02: [Current evidence-based workflow](apple-evidence-workflow.md) supersedes the reader, descriptions-only planner and guided matcher described below. The previous flow and experiments below remain relevant to the unchanged Gemma path and historical comparisons.

Choose a folder to build its document map. **Suggest categories** is available whether or not rules already exist, before starting Tuck. You may instead use the existing structure or write rules yourself.

Every readable mapped document first passes through the shared document-understanding stage. It produces a free-form description, a source-checked passage and a typed clear/unclear flag (normalized to uncertainty in the cache); it does not choose a predefined type, folder or filename. Successful descriptions are reused from `.tuck/cache/` when content and extraction match. The UI reports understanding progress, then grouping progress.

The coordinator retains document identity locally. The category provider receives a plain array of descriptions, without IDs or raw excerpts. Reduced batches retain a short category name and definition in each summary string. Collections of up to 32 descriptions and 6,000 description characters are planned together. Larger sets use batches within both limits, reducing related topics until one final call can propose one to six distinct subject-based categories. Reduction must reduce the number of entries; otherwise it stops with an error rather than looping. This reduction remains lossy; the prompt asks it to preserve specific subjects, but minor topics may still be missed. Model failures, unreadable inputs and descriptions that cannot be grounded are counted as skipped, and their documents stay in place. A suggestion with skipped documents is partial, not an exhaustive understanding claim.

Document extraction and prompts remain bounded. Long description inputs retain an opening and ending excerpt with an explicit omission marker; at most three read-only page/chunk/OCR requests can resolve missing evidence. This is not an exhaustive read of every page of arbitrarily long documents.

Edit the proposed names/rules and choose **Create folders**. This replaces the configured rules through the revision-checked save and creates missing destination directories. Existing directory contents are preserved; old category folders are not deleted. Documents do not move during setup. Return to Overview and **Start Tuck** to enable automatic filing.

The map includes up to 2,000 supported documents under 100 MB, scanning up to 10,000 entries and 32 directory levels. Destination rules remain at most 40 folders and two levels. Hidden paths and symlinks are excluded. A scan exceeding its limits fails before any organization. Individual document reads and model calls have timeouts; a large collection can take several minutes. Suggestions are in-memory drafts and are lost on app exit.

Rust tests cover safe category paths, stale configuration, unchanged source hashes and mapped all-document input. UI tests cover edits, removal, creation and discard. Historical three-document Apple category smoke tests do not establish accuracy for large collections; see [AI accuracy](ai-accuracy.md).

Category planning proposes only folder names and rules. Per-document assignment is a separate matcher stage after the user accepts the structure and starts Tuck. It receives category names and one document description with quotes, then returns a guided category choice or Needs input. Folder rules remain available to the subsequent verifier and naming stage. Use clear, descriptive folder names; the matcher cannot infer a special filing policy from a rule it does not see. All model workflows share the serial coordinator; see [AI architecture](ai-architecture.md). A refused category batch fails the proposal without creating folders. Category generation uses the explicitly approved Apple content-transformation mode for string responses; model refusals remain possible. Prompt/output validation fixes, mode behavior and measured results are documented in the [refusal investigation](../evals/reports/2026-10-01/refusal-investigation/README.md).

## Planner output validation and retry

Category planning uses ordinary string generation under the previously approved content-transformation policy. The response must be exactly one JSON object with a single `rules` array containing one to six entries, each with `folder` and `instruction`. A two-entry example makes the array structure explicit. Swift validates required fields, count, duplicate names, basic path/length constraints and generic catch-all names; Rust independently validates the returned category paths, rules and catch-all names.

Malformed JSON or an invalid draft gets one fresh attempt using the same descriptions and a request for one to six distinct subject-based categories with no required count. Nothing is silently truncated. The original 90-second helper timeout covers both attempts. A second invalid result fails the proposal without applying partial categories. Refusals, guardrail errors, timeouts and other model service errors are not retried by this mechanism. Raw responses are not logged in production.

The 2026-10-01 failure was reproduced in a 25-document local folder: the model inserted another `rules` key inside its array, which was invalid JSON. A separate reduction example returned 11 categories. A guided schema trial on the exact failing input refused, so it was not adopted. Description-only input and the bounded format/count retry address these observed failures without changing the model's guardrail policy.

Verification after the fix: offline Swift contract checks passed (malformed JSON, excess count, invalid paths, duplicate names, exhausted retry, and no retries on provider refusal/timeout); 80 Rust tests and Clippy passed. A read-only run across the affected 25-document folder returned four categories from nine confidently described files, with sixteen skipped. All source hashes were unchanged. This confirms the planner succeeds, not complete reader coverage or category accuracy.

## Useful category names

The planner groups by subject and is asked to keep unrelated topics separate. A name must help someone find a file: Travel, Identification, Employment or Education can be useful when supported by the collection. Documents, Personal Documents, Official Records, General, Other and similar catch-all labels are rejected. Subject-qualified names such as Medical Records and Education Certificates remain valid. This check applies to generated suggestions only; user-created categories are preserved.

The retry no longer forces exactly three categories. It repairs format or generic-label failures without imposing a count. This removes pressure to hide unrelated topics in one broad folder. Both the initial planning batches and final reduction use the same subject-specific instructions and validation. A generic result after the one permitted retry is a visible failure rather than an applied catch-all category. These checks reject known vague labels, not every possible vague meaning; semantic quality is checked in local evaluations.
