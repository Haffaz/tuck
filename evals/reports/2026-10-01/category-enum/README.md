# One-field guided category selection — 2026-10-01

## Follow-up without rules

The [subsequent simpler prompt](no-rules.md) removed rules/source labels from the matcher and reached **10/14** correct automatic folders with **zero refusals or guardrail errors**. That changes the interpretation below: the earlier rule-heavy examples failed, but a one-field guided schema can work on these documents. Production remains unchanged because the simpler variant still trails its recorded 12/14 result.

## Outcome of the first two variants

Implemented and tested in temporary helpers; **not adopted in production**. Both one-field guided variants filed 2/14 clear documents correctly, compared with 12/14 in the recorded approved production run. Each variant hit 12 matcher refusal/guardrail errors. The narrow schema removed manual parsing of model-generated JSON, but did not resolve the refusal problem. The working app source and installed application were preserved.

## What changed in the experiment

The prompt supplies a description, reader evidence, uncertainty, source labels, shared rules and allowed full folder paths with their own/parent rules. It asks for one category. A dynamic Apple schema constrains the answer to:

```json
{"category": "Finances"}
```

Here `category` is an enum of the actual enabled folders plus a collision-free `Needs input` fallback. The schema and prompt both explain the output. Tuck reads the field through `response.content.value(String.self, forProperty: "category")`; it does not parse an LLM-generated JSON string. Unknown folder values are still rejected defensively.

No document ID, quote ID, source ID, reason or page number is generated by the matcher. The adapter maps the selected folder to the existing internal index, carries the reader's first supporting quote forward and sends the full reader evidence to the unchanged verifier. Page/OCR requests remain with the reader. The experimental adapter does not manufacture a source-group exception for an ungrounded description; the existing coordinator's grounding and verification checks still apply.

Other roles, rules, fixtures, read limits, naming and verifier were unchanged. The existing approved model configuration was retained; Apple's guided generation still uses the default runtime guardrail behavior even when the supplied model selects permissive content transformations for string generation. Refusals were not retried as text responses.

## Two tested examples

1. **Illustrative example:** Recipes/Travel categories and a recipe returning `{"category":"Recipes"}`. The prompt explicitly says the real answer must come from the actual supplied categories.
2. **Aligned example:** the same instructions, but the example is an unreadable document returning the actual allowed fallback value, `{"category":"Needs input"}`. This removes the out-of-list illustrative value as a possible explanation.

The second example did not resolve the failures. It changed which individual documents succeeded, so examples can affect behavior even though both totals were equal. This experiment does not establish that every possible guided schema/prompt will fail or identify Apple's internal refusal cause.

## Results

All runs cover the same 16 synthetic fixtures: 14 clear documents and two deliberately unclear inputs. PDFs/images pass through native extraction. No personal documents were used or moved.

| Measurement | Existing production, recorded run | Guided, illustrative example | Guided, aligned example |
| --- | ---: | ---: | ---: |
| Correct automatic folders among clear docs | 12/14 | 2/14 | 2/14 |
| Wrong automatic folders | 0 | 0 | 0 |
| Clear docs needing input | 2 | 12 | 12 |
| Unclear docs left for input | 2/2 | 2/2 | 2/2 |
| Matcher refusals/guardrail errors | 0 | 12 | 12 |
| Matcher invalid-response errors | 0 | 0 | 0 |
| Median document time | 3.81 s | 2.13 s | 2.05 s |

The guided runs fail early, so their shorter times are not a speed improvement. This is a small known regression set, not a held-out or statistical accuracy estimate. The production column is the recorded immediately preceding evaluation, not a new simultaneous control.

Both the Swedish bank statement and Swedish home insurance text failed during matching in both variants. The illustrative example successfully filed the medical certificate and maintenance report; the aligned example successfully filed the injected-insurance fixture and maintenance report. Both unclear inputs selected the fallback. There were no typed-property decoding or malformed JSON errors; the framework raised refusal/guardrail errors before returning usable structured results.

## Reproduction

Apply either patch to a scratch copy of `src-tauri/swift` with the same directory layout, never to the working app merely to run this test. Compile its four files together:

```sh
swiftc -parse-as-library -O scratch/src-tauri/swift/TuckApple.swift scratch/src-tauri/swift/TuckRoles.swift scratch/src-tauri/swift/TuckRoleValidation.swift scratch/src-tauri/swift/TuckModelSupport.swift -o scratch/tuck-apple
```

Place a symlink named `tuck-reader` beside that helper pointing to the app's native reader. Run the existing live evaluation with `TUCK_EVAL_READER` set to that scratch reader, `TUCK_EVAL_FIXTURES` set to this directory's `fixtures.json`, and `TUCK_EVAL_REPORT` pointing to a new temporary JSON file:

```sh
cargo test --manifest-path src-tauri/Cargo.toml --lib live_apple_accuracy_eval -- --ignored --nocapture
```

The checked-in JSON reports additionally include per-stage timings captured by a synthetic-only wrapper. Production does not log document prompts or responses.

## Decision

Keep the current production matcher. A one-field schema is technically supported and produces a simpler successful result, but these two tested prompt/example combinations regress heavily because of refusals. This evidence supports retaining the working string-generation path rather than claiming schema simplification has solved the problem.
